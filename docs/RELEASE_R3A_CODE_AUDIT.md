# Аудит кода до R-3a «Скелетный ключ»

> Разделы исходного аудита ниже сохранены как снимок до исправлений. Итог работ и оставшиеся ограничения находятся в разделе «Исправления» в конце файла.

Последующая проверка в настоящем headless-браузере, дополнительные исправления и покрытие каждой страницы описаны в [HEADLESS_BROWSER_AUDIT.md](HEADLESS_BROWSER_AUDIT.md).

Дата: 2026-11-01. Проверяемая база требований: внешние `releases/R-1.md`, `R-2.md`, `R-3.md`, `R-3a.md`. R-0a/R-0b и последующие релизы исключены. Внешние документы прочитаны, не изменены.

## Вывод

Текущую сборку нельзя считать закреплённой реализацией R-3a. Есть поломки основных сценариев, несогласованность профиля и режима игры, незавершённые требования R-1/R-2/R-3. Оценщик ключей существует в коде, но отсутствует в сгенерированном каталоге, принимает неоднозначный текст за найденные ключи и не содержит наполненной базы оценок.

Это аудит, без исправлений приложения. Добавлены этот отчёт и автономный воспроизводитель `scripts/release-audit-repro.cjs`. Браузер, сеть, реальные профили и пользовательское хранилище не использовались. Формулы игры и реальную точность OCR по скриншотам не проверяли. Наличие кода не считается доказательством работоспособности всех его веток.

## Подтверждённые дефекты и разрывы

Приоритеты: P1 — основной сценарий не работает либо выдаёт существенно неверный результат; P2 — неправильный частный сценарий, неполное требование или системный долг. Номера ниже — устойчивые идентификаторы для последующего исправления.

### A01 — P1. Страница «Ключи» фактически лишена интерфейса

`tools/tarkovtool-keys.html`: body содержит заголовок и закрывающие div, но не loadBtn, gameMode, maps, mapsCard, tableCard, tbody, keysHead, search и другие ожидаемые элементы. `js/keys.js:163` безусловно присваивает `document.getElementById("loadBtn").onclick` и падает на null. Это не косметический дефект. При восстановлении разметки также нужно отключить autoLoad общего table engine: сейчас создан второй обработчик с пустым fetch.

Проверка после исправления: HTML-контракт должен видеть все необходимые элементы; загрузкой должен владеть ровно один обработчик.

### A02 — P1. Оценщика ключей нет в каталоге хаба

`hub/catalog.js` не содержит `tools/tarkovtool-key-analyzer.html`, хотя HTML с meta существует. Генератор обнаруживает 68 инструментов, текущий файл содержит 67. Дополнительно устарело описание keys. Генератор запускался только с `--check`, файл не перезаписывался.

### A03 — P1. PvP и PvE не имеют единого представления

`core/tarkov-profile.js:453`: профиль допускает `pvp`, а оценщик ключей показывает PvP как `regular`. `bindGameMode` при профиле pvp выбирает fallback pve; при ручном выборе regular записывает в профиль pve. Оба сценария воспроизведены отдельно. `TarkovAPI` передаёт режим в URL без общего адаптера.

Следствие: пользователь получает цены другого режима, а выбор PvP может изменить персональные настройки на PvE. Исправление должно определить отдельно режим профиля и имя режима внешнего API, а затем использовать единый преобразователь во всех инструментах. Действительность внешних endpoint здесь не проверялась.

### A04 — P1. Завершённый квест не открывает оффер торговца

`core/tarkov-profile.js:622–714`: наличие taskUnlock превращается в questLocked; gate при этом безусловно возвращает locked. Он не проверяет completed. Кроме того, offerMeta предпочитает название taskUnlock.name и теряет отдельный questId.

Воспроизведение: добавить quest-1 в completed, передать оффер с taskUnlock.id=quest-1 и name=Test quest → всё ещё «Квест: Test quest». Ошибка влияет на все инструменты, использующие offerGate, включая карточку предмета.

### A05 — P1. Поиск карточки предмета выбрасывает ReferenceError

`js/item-card.js:252,273`: itemLabel объявлена внутри showCard, но filterSuggest вызывает её из другой области видимости. После загрузки базы ввод строки, имеющей совпадение, вызывает `itemLabel is not defined`. Воспроизведено в VM.

### A06 — P1. Ценовая сирена не отправляет уведомления о найденном срабатывании

`js/price-alarm.js:186,190`: в обоих вызовах Notify передаётся необъявленная i18nParams. Ошибка ловится и только логируется. fired уже установлен, поэтому следующая проверка может не повторить попытку отправки.

Воспроизведение: цена 100, правило <=150 → hits=1, notifications=0. Наличие зелёного статуса проверки не гарантирует доставку уведомления.

### A07 — P1. Ценовая сирена не обновляет цены при повторном опросе

`js/price-alarm.js:60,200`: ensureCatalog навсегда возвращает загруженный массив, пока его явно не сбросят. checkOnce каждый раз обращается только к ensureCatalog. Это отдельная проблема от API TTL: вызов API вообще не повторяется.

Воспроизведение: две последовательные проверки → один вызов items. При любых последующих изменениях рынка сравниваются первоначальные цены.

### A08 — P1. Оценщик принимает общий текст за конкретный ключ

`js/key-analyzer.js:23–59`: строка `key` совпадает подстрокой с любым названием ключа, получает 80 и выбирает первый элемент каталога. Нет обработки неоднозначности, списка кандидатов или подтверждения выбора. Показатель Match% является эвристическим баллом, не вероятностью распознавания.

Воспроизведение: единственная строка key → Dorm room 114 key. На реальном скриншоте ошибки OCR могут незаметно превратиться в другой ключ, квесты и неверную сумму.

### A09 — P1. Требование «какие ключи хорошие для лута» не наполнено данными

`data/keys-rating.json`: ratings пуст. Оба инструмента берут score исключительно из этого файла; механизма оценки лутовой ценности вместо него нет. Все ключи без оценок получают прочерк. Это незавершённое требование R-3a, а не авария JS. Нужна содержательная база с источниками/методикой либо явно ограниченный статус функции.

### A10 — P2. Сумма комплекта теряет одинаковые экземпляры ключей

`js/key-analyzer.js:145`: seen удаляет все повторения одного ID, сумма считается по уникальным строкам. Два экземпляра стоимостью 100 дают 100 вместо 200. Воспроизведено.

Нужно различать повтор OCR одной ячейки и действительно разные ячейки. Простая отмена seen без пространственной модели тоже может завысить сумму. Текущий интерфейс не показывает количество и не даёт его исправить.

### A11 — P2. Смена профиля/режима не инвалидирует загруженную предметную базу

В `js/key-analyzer.js` render только вызывает wireToolPage; ранее загруженные catalog, questByKeyId, результаты и сумма сохраняются. В `js/item-card.js` render повторно показывает selectedId через прежний graph, без загрузки базы нового режима. В `js/price-alarm.js` внешний render не имеет доступа к renderRules из первого IIFE и не сбрасывает каталог.

Следствие: поля уже показывают новый режим, а информация остаётся от предыдущего. Нужен контракт данных с mode/profile revision и единая инвалидация, а не просто наличие bindRefresh.

### A12 — P2. Переходы из карточки теряют ID выбранной сущности

`js/item-card.js:211–249`: ссылки на квесты, крафты, бартеры и убежище содержат только путь страницы. ID виден рядом как текст, но не передаётся. `js/quests.js` не читает TarkovNav или ttId. Поиск использования TarkovNav в js находит только запись контекста из my-tarkov, но не сквозное потребление.

`core/tarkov-nav.js:90` отправляет tt-open-tool, однако обработчик этого типа в hub/core не найден. Затем функция всё равно меняет location текущего iframe. Требование R-2/R-3 «перейти к конкретной сущности без повторного ввода» не выполнено.

### A13 — P2. Два независимых набора ценовых алертов

`js/my-tarkov.js:139,263` читает/пишет TarkovState.alerts.prices со схемой slug/target/dir. `js/price-alarm.js:4,32` читает отдельный TarkovSchema-документ tarkovPriceAlarmRules со схемой id/q/metric/op/threshold. Связующий адаптер в этих сценариях не найден.

Созданный в «Мой Тарков» алерт не становится правилом сирены, удаление его в дашборде не удаляет правило сирены. Нужен один сервис правил и общий ID правила.

### A14 — P2. Экспорт/импорт всех профилей теряет активный профиль

`core/tarkov-profile.js:431`: экспорт содержит activeId, импорт назначает новые ID и активирует первый профиль, игнорируя activeId. Воспроизведение: выбрать A, экспортировать несколько профилей, импортировать → активируется ЧВК, стоявший первым. Нужна таблица oldId→newId и восстановление выбранного ID.

### A15 — P2. «Что я могу?» не вычисляет открытый контент

`core/tarkov-profile.js:720`: suggestActions не использует API/граф требований. Предлагает следующий УЛ каждому торговцу, общие уровневые подсказки и уже вручную заданные active quests. Нет проверки репутации/оборота/предыдущих заданий и нет сравнения состояния до/после изменения профиля для новых открытий. Наличие события изменения профиля не заменяет такую модель.

### A16 — P2. Фильтр доступных квестов учитывает только уровень

`js/quests.js:77–147,209–227`: onlyAvailable проверяет meetsLevel, а gate получает только minLevel. В модель строки не попадают зависимости taskRequirements и прочие ограничения. Квест с выполненным требованием по уровню и невыполненным предшественником может считаться доступным.

### A17 — P2. Персональный прогресс убежища общий для разных ЧВК

`js/hideout.js:43–48`: один tarkovHideoutProgress без profile ID; loadProgress вызывается при инициализации, при смене профиля отдельный прогресс не подгружается. Модель профиля хранит только notes.hideout, а не станции и собранные требования. Это разрыв системности: данные персонажа выглядят персональными, но фактически общие. Рынок/история цен могут быть общими по R-2; уровни станций — другой тип состояния.

### A18 — P2. Уклад схрона не моделирует количество одинаковых контейнеров

`js/stash-packer.js:5,72`: Set выбранных ID и checkbox на один тип предмета. Два одинаковых кейса невозможно задать как два объекта. Для реального набора пользователя нужна пара itemId/instanceId либо количество экземпляров до этапа упаковки.

### A19 — P2. Карточка и граф связей не полностью соответствуют R-3

`core/tarkov-item-graph.js`: usedInContainers объявлен, но не заполняется и не возвращается из links. Соответствующего раздела нет в полной карточке. Связи neededKeys квестов также не индексируются: граф учитывает objectives, а отдельные инструменты ключей независимо обходят neededKeys.

Бартерный индекс сохраняет barterKey/trader, но не count, а карточка выводит `o.count || 1`: количество каждого ингредиента/награды показывается как 1. Ветка magsFor группирует магазины по калибру, что не гарантирует совместимость с оружием. Для надёжного результата нужна общая нормализация ссылок и использование слотов/allowedItems из weapon domain, а эвристику следует явно отличать от подтверждённой связи.

### A20 — P2. Повторная реализация анализа предмета расходится с графом

`js/item-use.js:57–92`: отдельно разбирает крафты/убежище/квесты, вместо TarkovItemGraph. Для строковых itemRequirements один и тот же уровень убежища добавляется в hideNeeds двумя проходами; для объектных ссылок часть сравнений через `=== id` теряет связи. Результат крафта ищется через productItem, без общего rewardItems-адаптера. Хотя item-use исключён из нового каталога, страница остаётся доступной по прямой ссылке. Нужен единый источник связей или явное перенаправление старого инструмента.

### A21 — P2. Документация/справка не соответствуют состоянию и контрактам

`README.md` содержит только «Merge F1 over project; then build-catalog.». DESCRIPTION.md называет профиль будущим патчем в одном месте, а ниже описывает реализованный R-2. CONTRACT.md описывает прежний вес цены/доступности в рейтинге, тогда как domain уже использует pure quality/load. Контракт упоминает locale `.desc`, код использует `.description`.

В RU отсутствуют title/help для 23 из 70 страниц, description для 25; в EN — 22/22/24. Проверялись вложенные locale.tool[slug], с фактическим полем description. Fallback на meta может сохранить текст, но не даёт полного перевода и расширенной справки R-1. В price-alarm присутствуют повреждённые строковые литералы вида `Ð...`, в том числе статусы проверки.

### A22 — P2. Техническая интеграция оценщика не закончена

`tools/tarkovtool-key-analyzer.html:7` ссылается на отсутствующий ../styles.css. `js/key-analyzer.js` не освобождает предыдущий URL.createObjectURL при смене изображения. Ошибка загрузки tasks заглушается и превращается в пустой список: пользователь получает «Квестовых ключей не найдено» вместо сообщения о недоступности данных. Нужны раздельные статусы «нет связей» и «связи не загружены».

### A23 — P2. Смешанный генератор имён отбрасывает фракции до перемешивания

`js/names.js:80–94`: генерирует ceil(count/factions.length) от каждой фракции, затем делает slice(0,count), затем shuffle. При count=1 и нескольких выбранных фракциях в выборку всегда попадает только первая фракция. Нужно выбирать фракцию на каждый результат либо перемешивать общий пул до обрезки. Отдельно генератор boss дописывает свиту к имени босса, а не генерирует отдельное имя свиты; соответствие игровой базе имён в рамках этого аудита не проверялось.

## Системные причины

1. Контракты проверяют наличие символов/функций, но не результат работы. Поэтому 23 зелёные UX-проверки сосуществуют с падением item-card и отсутствием уведомлений.
2. Нет единой нормализации режимов профиля, API и HTML-контролов.
3. Нет единого жизненного цикла загруженных данных при смене mode/profile. render часто только перекрашивает старые данные.
4. Профиль централизован формально, но доступность, прогресс убежища и алерты ещё разнесены по независимым моделям.
5. Предметный граф существует параллельно с локальными вычислениями связей. Отсюда разные результаты и пропущенные количества/ключи/контейнеры.
6. Релизные документы, CONTRACT, meta, locales и generated catalog не проходят общую приёмку требований.
